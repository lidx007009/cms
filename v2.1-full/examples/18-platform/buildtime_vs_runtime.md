# 平台功能设计：开发态 vs 运行态 + Agent/Skill 编排

> 回答三个问题：① 方案里哪些是开发态、哪些是运行态；② 要不要"自研 AI 智能体 + Skill"，用在哪；③ 怎么让后期**业务方能自助开发报告 / 查看报告 / 追问**。

---

## 0. 一条总原则（整个平台的骨架）

> **开发态"产出制品(Artifact)"，运行态"消费制品"；中间隔一个【注册中心 + 发布门禁】。**

```
   开发态(Design-time / Studio)                注册中心(Registry)            运行态(Runtime)
  ┌───────────────────────────┐   发布(过评测门禁)  ┌──────────────┐  按版本拉取  ┌────────────────────────┐
  │ 语义建模 / 报告设计器 /     │ ───────────────►  │ 制品+版本+权限 │ ─────────►  │ 报告服务 / 追问Agent /  │
  │ Prompt台 / Skill注册 /      │                   │ (metrics/模板/ │             │ Skill执行 / 洞察调度 /  │
  │ 评测集 / 巡检规则 / 护栏策略 │   ◄─────────────  │ Prompt/Skill/ │  反馈/指标   │ 护栏 / 可观测           │
  └───────────────────────────┘   反馈飞轮回灌      │ few-shot...)  │ ◄─────────  └────────────────────────┘
                                                     └──────────────┘
```

制品都是**带版本、可灰度、可回滚**的：metrics 定义、报告模板+映射契约、章节 Prompt、Skill 定义、few-shot、巡检规则、护栏策略、评测集。运行态永远只跑"已发布版本"。

## 1. 组件归属表（每个能力是开发态还是运行态）

| 2.1 组件 | 开发态(设计/编排/构建) | 运行态(在线/调度) | 是否 Agent+Skill |
|---|---|---|---|
| 语义层 metrics 定义 | ✅ 建模、认证 certified、配预聚合 | 查询编译执行(引擎) | — |
| 报告模板 + 映射契约 | ✅ 报告设计器拖指标→自动绑定→schema校验 | 渲染时按契约取数 | — |

| 版本快照 + 血缘 | — | ✅ 生成报告时冻结、查看时读取 | — |
| MCP 技能 / 语义查询 | ✅ Skill 注册中心(定义+入参schema+权限+认证) | ✅ Skill 执行服务(校验+权限+下推) | ✅ Skill |

| 评测框架 | ✅ 金标准集编写、门禁配置 | 发布门禁(CI)/线上影子评测 | — |
| 可观测 + 缓存 + 模型路由 | 配置 | ✅ 在线 Trace/缓存/路由 | — |
| 主动洞察巡检 | ✅ 检测器/阈值/推送策略配置 | ✅ 定时任务执行+推送 | 部分用 Skill(归因/叙事) |
| 反馈飞轮 | few-shot 晋升/淘汰治理 | ✅ 反馈采集(在线) + 回灌(离线调度) | — |

## 2. 平台模块架构（建议的产品形态）

### A. 开发态平台 —— "AI 报告 Studio"（给数据/AI/产品/业务用）
1. **语义建模台**：维护 `metrics.yaml`、字段字典、预聚合；指标**认证(certified)**流程。
2. **报告设计器(低代码)**：业务方拖拽**已认证指标**进模板槽位 → **自动生成映射契约** → 配章节解读(可用默认 Prompt) → **试生成预览** → 提交评测 → 发布。这是"业务能自助开发报告"的关键。
3. **Prompt 工作台**：编辑章节推理 Prompt + 结构化 schema，版本化、A/B、回滚。
4. **Skill 注册中心**：注册 MCP 工具(入参 schema、权限、口径、认证)，开发态登记、运行态调用。
5. **评测台**：金标准集管理、跑分、门禁、回归对比。
6. **巡检规则台 / 护栏策略台 / few-shot 治理台**。

### B. 运行态服务（在线 + 调度）
1. **报告生成服务**(按需/定时)：绑定→取数→快照→解读→渲染。
2. **报告查看服务**：读快照、渲染、图表、提供"追问入口"。
3. **追问 Agent 服务**：编排循环(护栏→路由→RAG→工具→结构化→数值自校验)。
4. **Skill/MCP 执行服务**：受控语义查询、权限注入、审计。
5. **语义层查询引擎**：编译+预聚合+缓存+下推。
6. **主动洞察调度** / **护栏中间件** / **可观测·缓存** / **反馈采集**。

### C. 共享基础
**注册中心(制品+版本+权限)** / **快照存储** / **向量库** / **权限中心(行级)** / **可观测后端** / **缓存**。

## 3. 三条用户旅程（开发态/运行态怎么衔接）

### 旅程一：业务"开发报告"（开发态；两种方式互补）
**方式 A — 对话式 AI 智能体（推荐快速起草）**：用"报告开发 Copilot(Authoring Agent)"，业务说需求 → AI 推荐 certified 指标、起草契约与章节 Prompt、试生成预览 → 人确认编辑 → 过评测 → 发布。详见 `report_authoring_agent.md`。
**方式 B — 低代码设计器（推荐精修）**：拖拽已认证指标到槽位、像素级排版。
```
[开发态] (Agent 起草 或 设计器拖拽) → 自动生成 semantic_binding.json(系统生成)
       → 配/起草章节解读 Prompt → 试生成预览(调一次运行态生成) → 跑评测
       → 人确认发布(产出"模板+契约"新版本进注册中心)
```
要点：无论哪种方式，业务方都**只能选 certified 指标**，绑定由系统生成、schema 自动校验、发布过评测门禁 → **业务自助但不失控**。推荐"**Agent 出 80% 草稿 + 设计器做 20% 精修**"。

### 旅程二："查看报告"（运行态）
```
[运行态] 用户打开报告 → 若已定时生成→直接读快照渲染；若按需→触发报告生成服务→冻结快照→渲染
       → 页面内嵌"追问入口"
```

### 旅程三："追问"（运行态，Agent+Skill）
```
[运行态] 用户提问 → Guardrails(输入关) → 小模型路由/缓存 → 注入记忆+RAG召回
       → 追问Agent编排：选 Skill(run_semantic_query/resolve_entity/forecast...) → Skill执行服务(权限+下推)
       → 结构化输出(文字+Vega) → Guardrails(输出关)+数值自校验 → 更新焦点 → 采集反馈
```

## 4. 要不要"自研 AI 智能体 + Skill"？用在哪？（建议）

**结论：要，但用对地方、用对形态。**

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 生成报告 | **工作流编排(非 Agent)** + 章节 LLM 调用 | 流程确定、步骤固定，用 Agent 反而不稳；确定性 pipeline 即可 |
| 报告内追问 | **单编排 Agent + 受控 Skill(MCP)** | 问题不确定、需意图理解与工具编排，正是 Agent 的价值 |
| 主动洞察 | **离线管道 + 复用归因/叙事 Skill** | 定时批处理，部分步骤调 Skill，不需要对话式 Agent |

**Agent 形态建议（关键，别过度设计）**：
- 用**单个"编排 Agent"(orchestrator)** 调用一组**强类型 Skill**，**不要多 Agent 群**(复杂、易失控、ROI 低)。
- **Skill = 你自研的受控业务能力**(语义查询/实体消歧/预测/元数据检索)，用 **MCP 标准**暴露 → 换模型/接第三方不返工。
- Agent 运行时可**基于成熟编排框架**(如 LangGraph 等)落地，**业务 Skill 自研**；即"**自研业务 Skill + 标准 Agent 运行时 + 受控编排 + 强护栏**"。
- Agent 必须被 **Guardrails 包裹 + 步数上限 + 数值自校验 + 只能调注册 Skill**，杜绝自由发挥。

## 5. 是否有"更好的设计"？—— 推荐的目标架构（5 条增强）

1. **以"注册中心 + 制品"为唯一契约**：开发态产物(metrics/模板/Prompt/Skill/few-shot/规则)全部制品化、版本化，运行态只消费已发布版本。**这是把方案从"一堆脚本"升级为"平台"的核心。**
2. **环境分离 + 灰度/影子发布**：dev/staging/prod 三套；Prompt/Skill/few-shot 改动先影子跑、灰度放量，异常一键回滚。
3. **低代码报告设计器 + 只能选 certified 指标**：直接满足"业务后期能自助开发报告"，且口径受控、契约自动生成、CI 自动校验。
4. **能力统一注册(Capability Registry)**：报告生成、追问、预测、洞察都视为"能力"，统一注册、统一鉴权、统一可观测；追问 Agent 通过同一套 Skill 目录发现能力 → 加新能力=注册新 Skill，不改 Agent。
5. **开发态也接评测门禁**：报告/Prompt/Skill 发布前必须过评测(blocker 100%)，把质量左移到开发态，而不是上线后救火。

> 一句话总结更好的设计：**"语义层做口径地基 + 注册中心做开发/运行契约 + 单编排 Agent 调受控 Skill + 低代码设计器让业务自助 + 评测门禁与灰度兜住质量"**。既能让业务自助开发/查看/追问，又始终把"取数、权限、口径、安全"牢牢攥在平台手里。

## 6. 平台落地分期（建议）
| 期 | 开发态 | 运行态 |
|---|---|---|
| P1 | 语义建模台 + 报告模板/契约(可先 YAML/JSON 手维护) + 评测集 | 报告生成+查看服务 + 快照 |
| P2 | Skill 注册中心 + Prompt 工作台 + RAG 索引构建 | 追问 Agent + Skill 执行 + 护栏 + 可观测 |
| P3 | 低代码报告设计器 + 巡检/护栏/few-shot 治理台 + 灰度发布 | 主动洞察调度 + 反馈飞轮 + 预测 + 长期记忆 |
